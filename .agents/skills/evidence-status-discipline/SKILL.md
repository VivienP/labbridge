# Evidence status discipline

This project is judged on the honesty of its claims as much as on its code. A guarantee that no test at
an adequate layer proves is a plan, not a guarantee.

Authority: `AI_CONTRACT.md` invariant 10 and §10; `docs/ARCHITECTURE_DECISIONS.md` ADR-008.

## The four statuses

| Status | Means | Promotion requires |
|---|---|---|
| `planned` | specified, not implemented | code |
| `implemented` | code exists and its relevant local automated tests pass | a reproducible artifact or operational experiment |
| `demonstrated` | a reproducible artifact, manifest, or operational experiment proves it | — |
| `deferred` | intentionally outside the current release | a scope decision |

Every material capability carries exactly one. A capability described with no status is a finding.

Code existing is never sufficient for `demonstrated`. Tests passing is never sufficient for
`demonstrated`. Only an inspectable artifact you can name is.

## The mechanism-versus-guarantee substitutions

These are the specific overclaims this architecture invites. Use the right-hand column.

| Do not write | Write instead | Why |
|---|---|---|
| exactly-once execution | at-least-once delivery with idempotent effect handling; at most one accepted outcome per intended attempt | The worker protocol is at-least-once (ADR-002). Uniqueness constraints deduplicate *effects*; they do not make *execution* exactly-once. |
| deterministic execution | deterministic state reconstruction from the ordered event stream | Invariant 6 promises replay reproduces logical state. Infrastructure timing may differ between executions. |
| guaranteed no data loss | no accepted observation lost across the tested process-termination boundaries | A guarantee is universal; a test covers the boundaries it injected. Name them. |
| production-ready | deployed and operated under the documented runbook, with the recovery evidence in `<artifact>` | `docs/ROADMAP.md` open operational gaps: a cloud URL is not production proof. |
| demonstrates / proves | implements, when there is no artifact | Reserve for `demonstrated`. |
| fault-tolerant | fault-aware: every failure produces a durable outcome and a classified failure code | Tolerance implies continued correct service; awareness is what the design provides. |
| calibrated uncertainty | model uncertainty from `<policy>`, uncalibrated | `AI_CONTRACT.md` §11 forbids calibrated-uncertainty claims without a defined calibration procedure and evaluation. |
| reproduced the published fit | recomputed an independent fit; agreement with the source-provided fit is `<status>` | `docs/DATA_STRATEGY.md` §2.5 blocks reproduction claims until tolerances, eligible records, and method correspondence are documented and tested. |
| real / measured / experimental data (for simulator output) | synthetic data generated by the seeded phenomenological simulator | Invariant 1. |
| a live experiment / a lab run (for replay) | a replay of historical observed measurements | `docs/DATA_STRATEGY.md` §1. |
| digital twin / validated model | mechanistically informed phenomenological simulator | `docs/SIMULATOR_MODEL.md` §1. |
| zero lost observations (before the experiment) | the acceptance target is zero lost observations; measured results pending | `docs/FAILURE_MATRIX.md` §6: *"These values are targets until measured."* |

## Numbers

Every number in committed documentation must point to an inspectable artifact that exists **today**:
a committed result file, a manifest, a test report, or a documented operational experiment.

If the run has not happened, the document says so. It does not carry a placeholder, an estimate, an
expected value, or a target presented as a result.

A number that appeared in a commit message, a report you wrote, or a previous session is not an
artifact.

## Before promoting any claim

1. Name the artifact. If you cannot give its path, the claim is not `demonstrated`.
2. Confirm the artifact is reproducible from recorded inputs and versions (invariant 12).
3. Confirm the artifact is covered by a manifest with hashes and producing versions.
4. Confirm `labbridge validate-artifacts` passes on it, once that command exists.
5. Confirm the wording matches the mechanism actually proven, using the substitution table above.
6. Confirm the failure or limitation the artifact does **not** cover is stated alongside it.

## Report language for synthetic output

Every simulator report carries language equivalent to the paragraph in `docs/SIMULATOR_MODEL.md` §13.
Charts carry "Synthetic" in the title or subtitle. Tables expose `data_origin` and the simulator
version. A synthetic export with no visible and machine-readable label is an integrity-gate failure
(F-045), not a formatting problem.

## Scope

Apply to: `README.md`, everything under `docs/`, docstrings and module docstrings, CLI help text,
generated report text and chart labels, commit messages, and your own completion reports.
